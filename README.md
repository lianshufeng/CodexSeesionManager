# Codex Session Manager

Codex Session Manager 是一个面向 Windows 的 Codex 账户管理工具，核心能力是通过本地代理自动接管 Codex 请求，在多份 Codex 授权之间自动选择更合适的 session 使用。

它的重点不是手动复制 token，而是让 Codex 客户端继续按原方式运行，由代理层根据当前账户额度自动改写请求中的 `Bearer accessToken`，实现多账号无感切换和自动负载。

## 核心能力

- 通过程序登录流程维护本地 `auth/` 授权管理目录。
- 自动读取每个授权的账号 ID、计划类型、额度、额度刷新时间和访问令牌。
- 默认开启自动负载，优先选择 5 小时剩余额度更高的 Codex session。
- 代理层会对请求头中的 `Bearer accessToken` 做统一替换，不绑定单一接口 URL。
- 自动统计被实际使用的 token 流量，并在授权表中展示。
- 代理空闲超过 5 秒时重新选举负载目标。
- 检测到旧长连接仍在消耗非目标 token 时，会等待 WebSocket ping/pong 时机断开旧连接。
- UI 中用“当前”和“负载”两列区分源授权文件和自动负载目标。

## 自动负载的工作方式

程序启动后会创建一个本地 mitmproxy 代理，并启动一个内部控制通道。Codex 进程通过该代理访问网络时，代理插件会把请求中的 `Bearer accessToken` 替换为当前自动负载选中的 access token。

自动负载目标由 UI 侧维护：

1. `AuthSyncService` 管理程序登录流程保存到 `auth/` 目录的授权。
2. `AuthUsageService` 定时请求 ChatGPT usage 接口，刷新每个授权的额度、计划类型和额度重置时间。
3. `ProxyWindow` 根据授权表中未禁用账号的额度计算优先级。
4. 选择 5 小时剩余额度百分比最高的授权作为“负载”目标。
5. `ProxyLoggerAddon` 在每个代理请求进入时获取目标 access token，并改写请求头。

开启“额度预热”后，会先从未禁用且所有已解析额度均大于 0% 的授权中，选择 5 小时剩余额度不低于 99% 的账号。没有符合条件的账号时，恢复原有的“优先/正常”负载策略。

后台自动预热已启用，由“额度预热”开关控制，同时保留上述高额度账号选号功能。

候选账号先等待 30～180 秒错峰时间（按每分钟检查节奏执行，每轮最多发送一个账号），计划发送时间持久化，重启不会重新抽取。请求使用简短算术或常识问题并限制简短回答；UA 使用真实系统信息和管理器身份。启用时区覆盖时使用软件设置，否则使用本机默认时区。补偿间隔至少 5 分钟，另加 0～120 秒抖动，并再次安排错峰时间。服务端 Retry-After 会延长拒绝后的退避时间。这些措施用于错峰和配置一致性，不保证避免风控。

后台每分钟检查额度窗口，对第一个窗口剩余额度为 100% 的可用账号发送预热 ping。发送前保存第一个窗口的绝对重置时间，请求完成至少一分钟后独立查询：重置时间基本不变表示窗口已启动，即使额度仍显示 100% 也不再发送；重置时间明显后移表示预热未生效，距上次发送满 5 分钟后继续尝试，不限制次数，每次发送前重新检查额度和授权状态。超时或中断后同样先验证，未生效则继续补偿；验证连续失败满 5 分钟后也允许重新尝试，但发送前必须成功读取额度。已启动账号提前重置并恢复 100% 时重新检查。验证基准、发送记录和重试时间会持久化，重启或更换预热模型不会跳过验证或重试间隔。Tooltip 展示状态及最近发送、确认时间。

因此，“当前”授权表示 `~/.codex/auth.json` 当前指向哪一份授权；“负载”授权表示代理实际优先让 Codex 消耗哪一个 session。自动负载开启时，这两者可以不是同一个账号。

## UI 标记说明

授权表主要字段：

- `当前`：当前写入 `~/.codex/auth.json` 的授权。
- `负载`：自动负载选中的授权，Codex 请求会优先使用它的 access token。
- `账户id`：授权对应的 Codex 账户。
- `令牌刷新时间`：授权文件中的 token 刷新时间。
- `额度刷新时间`：usage 接口返回的 5 小时窗口 reset 时间。
- `额度(5h/7d)`：usage 接口返回的 5 小时和 7 天额度摘要。
- `类型`：账号计划类型。
- `流量`：该 token 被代理实际使用的次数。

底部和托盘提示显示输出速度，例如 `35.0 token/s`，每秒更新一次，按最近 3 秒收到的实际输出文本用 o200k_base 分词器计数。支持 HTTP/SSE 与 WS 的文字、代码、工具参数、可见思考文本及摘要；新增文本增量事件也可计入。协议字段、心跳、图片/音频数据不计入；增量与最终全文共用状态，避免重复计数。统计不绑定账号、不依赖客户端请求或 response.created，并合并代理经过的多个会话；不代表单个会话的速度，也不包含服务器未返回的隐藏思考。压缩响应先解压、兼容跨块 UTF-8。后台统计使用有界缓存；空闲显示 `0.0 token/s`。升级统计口径后首次启动重置旧历史。

托盘每 10 秒检查一次实际注册状态，图标丢失后自动重新添加，暂时失败时继续重试。

点击底部的 token/s 数字可打开输出速度历史折线图，查看最近 5 分钟、30 分钟或 1 小时的每秒速率、平均值和峰值。记录保存在 `data/token_speed.sqlite3`，后台每 10 秒批量写入，默认保留 7 天；正常退出会写入剩余记录，异常退出可能丢失最近约 10 秒。空闲记录为 0，程序未运行的时间显示断档。图表只在打开时刷新，不额外保存正文或授权令牌。

右键授权行可以切换、禁用或删除授权。禁用后的授权不会参与自动负载选举。

## 使用流程

1. 以管理员身份启动程序。
2. 程序会启动本地代理，并自动检查或安装 mitmproxy 证书。
3. 在“安装项”中选择 Codex 可执行程序并点击启动。
4. 启动脚本会给 Codex 设置 `HTTP_PROXY`、`HTTPS_PROXY` 和 `ALL_PROXY`，让 Codex 请求经过本地代理。
5. 保持“自动负载”开启，程序会自动选择额度更充足的 Codex session。
6. 需要手动切换源授权时，双击授权行或右键选择“切换”。

## 容量错误自动重试

管理器启动 Codex 桌面版时默认开启本机调试端口 9222，不受“自动重试”开关影响。“自动重试”开关位于“连接配置”中、“自动负载”右侧，默认关闭，选择会保存到 `config.json`；只有勾选后才自动检查和点击，取消勾选后停止扫描和自动点击，切换开关无需重启 Codex。升级前已运行且未开启调试连接的 Codex，仍需完全退出后从管理器启动一次。命令行版 Codex 不使用此功能。

后台每 5 秒检查模型容量不足的错误卡片，包含普通请求及远程压缩任务。只搜索卡片内的按钮，按包含关键词匹配“重试”“重置”“重新尝试”“再试一次”及英文 `Retry`、`Try again`、`Reset`，同时检查按钮文字和 `aria-label`。按钮禁用、隐藏或仍有秒数倒计时时等待；实际点击后，该会话冷却 30 秒，之后继续检查并重试，不限制次数。错误消失后继续待命，调试连接断开后持续尝试恢复。

侧栏已加载且带错误标记的其他会话会被轮流打开检查，重试后返回原会话；用户输入或主动切换会话时暂停自动导航。尚未加载到侧栏的会话不保证覆盖。跨窗口及页面重载共享会话冷却记录，退出管理器时停止监控。

管理器可通过 `--remote-port 9233` 指定其他调试端口，或使用 `CODEX_DEBUG_PORT` 环境变量（命令行参数优先）；`--remote-port 0` 关闭调试连接及自动重试，`CODEX_AUTO_RETRY=0` 仅禁用自动重试。

## 长连接与流量矫正

Codex 可能存在 WebSocket 或其他长连接。目标 token 切换后，旧连接不一定会立刻断开。程序会做两类处理：

- 当代理超过 5 秒没有数据输出时，触发一次负载目标重新选举。
- 当检测到实际消耗 token 和当前负载目标不一致时，等待下一次 WebSocket ping/pong，再断开旧连接。

如果需要主动处理旧连接，可以点击“矫正流量”。程序会先刷新额度，再请求代理断开当前跟踪到的长连接。

## 配置与数据

- `config.json`：保存监听端口、二级代理、自动负载和额度预热开关。
- `auth/`：保存程序登录流程产生的授权及管理器私有配置。
- `.mitmproxy/`：保存 mitmproxy 证书文件。
- `logs/`：保存运行日志。

自动负载默认开启。如果关闭自动负载，代理会保留原始 token 的计数逻辑，不再主动替换为选举目标。

## 远程状态服务的 MQTT 协议

远程状态服务使用 Mosquitto，同时接受 MQTT 3.1.1 和 5.0 客户端连接同一个端口。Postman 可以选择 V3.1.1 或 V5。服务随手动注入启动，停止时会结束其启动的 Mosquitto 子进程。

监听地址默认为 `0.0.0.0`，账号密码沿用窗口配置，默认 `admin` / `admin@2026`。其他机器使用本机实际 IP 和配置端口连接。附加后在 Codex 中切换会话，窗口显示“可写”后即可发送命令。写端通过父进程发送与目标 App Server 接收的两条相同请求确认，使用独立异步完成事件写入原管道，支持桌面端空闲时主动投递。

订阅 `codex/<PID>/observed/input`、`codex/<PID>/observed/output` 接收协议事件，订阅 `codex/<PID>/status` 查看 `attached` 和 `writerReady`。向 `codex/<PID>/command` 发布下面的 JSON，并订阅 `codex/<PID>/reply/demo_001` 接收结果。

订阅固定主题 `codex/status` 可以发现当前目标，状态包含 `pid`、`attached`、`writerReady` 和 `runId`。同一桌面进程下唯一的新 App Server 接管后，请改用新 PID 的主题。观察流出现缺口时，`codex/<PID>/observed/gap` 会报告缺失。

```json
{"id":"demo_001","method":"thread/start","params":{"cwd":"E:/git/github/docker-codex"}}
```

从结果取得 `result.thread.id`，再使用新的请求 ID 发布 `turn/start`。

```json
{"id":"demo_002","method":"turn/start","params":{"threadId":"替换为会话ID","input":[{"type":"text","text":"请阅读项目 Dockerfile，用中文解释其构建与启动流程。"}]}}
```

普通请求按标准 app-server JSON-RPC 转发，方法支持情况由 app-server 返回，桥不逐项维护业务方法白名单。会话命名使用 `thread/name/set`，参数为 `threadId` 和 `name`，名称直接保存到执行端。桌面连接已经完成初始化，桥拒绝重复的 `initialize` 和 `initialized`。轮次最终结果通过 `observed/output` 的 `turn/completed` 事件接收。`rpc/respond` 可以回答仍待处理的审批或提问，`params` 传 `requestId` 和协议要求的 `result` 对象，其回包仅确认回答已写入。审批和提问的事件仍会送达原桌面界面。

命令关闭 Retain。请求 ID 在本次附加期间应保持唯一，近期重复 ID 返回已缓存回包。桥不设置累计请求数、业务并发数或单条 JSON 的业务上限，MQTT 协议和管道背压仍适用。状态公布 `methods: "*"`、`protocolVersion: 1`、`runId`、`maxRequestBytes: null` 和 `fileTransfer`。文件使用独立 MQTT 二进制主题，每块 512 KiB，不设置文件总大小上限。请求、响应和观察事件均保留原始业务字段，不按方法或字段名过滤。MQTT 账号可接收执行端协议事件，需作为可信后端凭据保管。投递不确定时先查询执行状态，避免重复提交。当前监听为普通 TCP，公网加密接入可由外部 TLS 通道提供。

Windows 源码运行时，从 [Mosquitto 官网](https://mosquitto.org/download/) 安装 Broker，或将官方运行文件及所需 DLL 放入程序根目录的 `mosquitto/`。也支持从 PATH 查找。Mosquitto 是外部运行文件，Python 依赖仍统一在 `requirement.txt` 中维护。构建前需准备好 Mosquitto，打包配置会收集 Broker、DLL 和许可文件。

## 构建发布

仓库包含 GitHub Actions 工作流，可在 GitHub 页面手动触发 Windows 构建。触发后会使用 GitHub Windows 主机打包程序，并按北京时间生成形如 `202605061739` 的 tag 发布 zip 包。

本地打包复用现有 `setup.py`：

```bat
python setup.py build
```

构建产物包含 `codex_session.exe`、`mitmdump.exe`、代理插件、图标和运行所需依赖。
